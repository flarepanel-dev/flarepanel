# Deploy to Cloudflare

:::warning
This is the manual path the hosted service uses. It works, but expect rough edges while FlarePanel is in early access.
:::

::::steps

### Get the code

```bash
git clone https://github.com/flarepanel-dev/flarepanel.git
cd flarepanel
bun install
bunx wrangler login
```

### Create the resources

```bash
bunx wrangler d1 create flarepanel
bunx wrangler queues create flarepanel-jobs
bunx wrangler queues create flarepanel-jobs-dlq
bunx wrangler r2 bucket create flarepanel-events
```

Put the D1 database id from the first command into `apps/worker/wrangler.jsonc` (`d1_databases[0].database_id`).

### Point it at your domains

In `apps/worker/wrangler.jsonc`, set the `routes` custom domain and the `API_URL`, `DASHBOARD_URL` and `CUSTOM_COOKIE_DOMAIN` vars. In `apps/start/wrangler.jsonc`, set the dashboard's custom domain and the same two URLs.

Make sure both files' `vars` have `"SELF_HOSTED": "true"`. It is the switch between a self-hosted install and the hosted service: with it there are no plans, trials or billing pages, and limits are yours to set.

### Add the secrets

```bash
cd apps/worker
openssl rand -hex 32 | bunx wrangler secret put COOKIE_SECRET
openssl rand -hex 32 | bunx wrangler secret put AUTH_SECRET
openssl rand -hex 32 | bunx wrangler secret put ENCRYPTION_KEY
```

`ENCRYPTION_KEY` encrypts the credentials FlarePanel stores for you: S3 and GCS export keys and Search Console tokens. Without it, saving an export fails. Keep it stable: if you replace it, stored credentials can no longer be read and have to be entered again.

### Expire AI text and session replays in R2

Prompt and response text of [AI calls](#ai-analytics) and [session replays](#session-replay) are kept 30 days, like OpenPanel's. Add lifecycle rules so R2 removes them after that:

```bash
bunx wrangler r2 bucket lifecycle add flarepanel-events ai-text-30-days ai/ --expire-days 30
bunx wrangler r2 bucket lifecycle add flarepanel-events replays-30-days replays/ --expire-days 30
```

### Migrate and deploy

```bash
bunx wrangler d1 migrations apply flarepanel --remote
bunx wrangler deploy
cd ../start && bun run deploy
```

### Check it

Open `https://api.example.com/healthcheck` (it answers `{"ready":true,...}`), then sign up on your dashboard domain and create a project.

## Optional features

These need a key or an external account. Everything else works without them.

### Google Search Console (SEO page)

1. In [Google Cloud](https://console.cloud.google.com/), create or pick a project, enable the **Google Search Console API**, and set up the OAuth consent screen with the `https://www.googleapis.com/auth/webmasters.readonly` scope.
2. Create an **OAuth client ID** of type **Web application** with the authorized redirect URI `https://api.example.com/gsc/callback` (your API domain).
3. Add the client to the API Worker:

```bash
cd apps/worker
bunx wrangler secret put GOOGLE_CLIENT_ID
bunx wrangler secret put GOOGLE_CLIENT_SECRET
bunx wrangler secret put GSC_GOOGLE_REDIRECT_URI   # https://api.example.com/gsc/callback
```

Then connect a site under a project's **Settings → Google Search**. Search Console numbers are synced daily (six months back on connect) and stored in the project's Durable Object.

### AI chat assistant

The dashboard's **Chat** and the natural-language filters call a language model. Add one provider key:

```bash
bunx wrangler secret put OPENAI_API_KEY     # or ANTHROPIC_API_KEY
```

Each message is billed by that provider to your account. Without a key, Chat and the natural-language filters stay unavailable.

### S3 exports with an IAM role

S3 and GCS exports work with access keys or a service-account key that you enter in the dashboard. Exports that **assume an IAM role** need an AWS identity for the server to assume it from:

```bash
bunx wrangler secret put AWS_ACCESS_KEY_ID
bunx wrangler secret put AWS_SECRET_ACCESS_KEY
```

## AI analytics

AI calls sent with `@flarepanel/ai` (or `op.ai`) are stored per call in the project's Durable Object. Prompt and response text waits there until its trace is quiet for 5 minutes, then moves to R2 as one gzip file per trace (`ai/<project>/<trace>.json.gz`) and is shown for 30 days.

## Session replay

Turn it on in the web SDK with `sessionReplay: { enabled: true }` (and `sampleRate` to record a share of sessions). Inputs and text are masked by default. Each recorded chunk (about every 10 seconds of activity) is stored gzip-compressed as one R2 object under `replays/<project>/<session>/`, and the project's Durable Object marks the session so the Sessions pages show **Watch replay**. Chunks for sessions the project never saw are refused.

Every organization records, up to **10,000 recorded sessions a month** each. That keeps a small install inside R2's free writes; past it, new sessions are not recorded until the 1st of next month (sessions already recording finish), and nothing breaks. To change it:

```bash
echo 50000 | bunx wrangler secret put FLAREPANEL_REPLAY_MONTHLY_SESSIONS   # 0 = unlimited
```

One organization can get its own limit, or be switched off ([Operations](/self-hosting/operations#session-replay-limits)). The Sessions page warns at 80% of the limit and when it is reached.

Cost: one R2 write per chunk (the first million each month are free, then $4.50 per million) and the stored bytes for 30 days (10 GB free, then $0.015 per GB-month). Check current prices on Cloudflare's R2 pricing page. A 5-minute session is about 30 writes; watching it reads 40 chunks at a time.

## Imports and exports

- **Imports** (Umami CSV files, Mixpanel and Amplitude) need the R2 bucket: the source is copied to `imports/<project>/<import>/` and read in short steps, then removed when the import ends. A Mixpanel rate limit pauses the import instead of failing it.
- **Exports** to S3, S3-compatible storage (R2, MinIO, Spaces) and Google Cloud Storage run every minute. Raw events are not removed from a project's Durable Object before every running export has uploaded them.

## Costs

Idle projects cost nothing: no alarms run once their sessions have ended. Each tracking request is one Worker request and one Durable Object request; events are written in batches, so storage writes stay well below one row per event at steady traffic. Set per-Worker CPU limits and a billing alert in your Cloudflare account.

## Email

To send account emails, onboard your domain under **Compute → Email Service → Email Sending** (or `wrangler email sending enable your-domain.com`) and keep the `send_email` binding in `apps/worker/wrangler.jsonc`. Workers Paid includes 3,000 emails a month.
